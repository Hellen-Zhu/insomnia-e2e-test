E2E 自动化框架：能力总结、三方案对比与风险对冲

基于 Playwright Test（TypeScript）+ playwright-bdd 的交易门户 E2E 框架已完成搭建与试点验证。本文总结框架能力，对比公司内部 genie-playwright（Java）与 Python 方案，并正面回答 playwright-bdd 的维护风险问题。

结论先行

一句话建议

Trade Portal 的 E2E 选用 TypeScript + Playwright Test：与被测前端同语言，独占官方旗舰 runner（fixtures 依赖注入、自动并行、trace、UI Mode）与 AI 工具链演进；BDD 层（playwright-bdd）作为可插拔的薄层引入，其维护风险已通过架构隔离和一条经过实测的退出路径对冲。

推荐什么
TS + Playwright Test

官方第一优先级语言绑定，runner 能力最全；BDD 为可选薄层，业务语言与实现解耦。

为什么不是另两个
runner 与协作面差距

Java/Python 绑定没有 Playwright Test runner；genie 生态的集成优势可以通过报告桥接获得，runner 能力无法桥接。

最大风险
playwright-bdd 个人维护

耦合面仅占代码 21%，且已维护一个不含 BDD 的镜像分支实证退出路径——风险可量化、可退出。

八项核心能力

业务语言规范（六规则词汇表）

业务状态是封闭短语而非参数（如 the trade is approved and marked as new，裁决 × 状态双维锁定）；表外措辞直接编译失败，词汇不会静默漂移。规范沉淀在 docs/gherkin-style.md。

数据驱动三层设计

caseId 写进场景标题绑定 YAML 用例；全局懒加载索引 + 命名空间（cases / *_preset），跨文件重复 key 与 typo 键构建期报错；深拷贝取数保证并行安全。caseId 未来可机械替换为 ADO work item ID。

POM 纪律：Locator 收口

固定元素一律类头部 readonly 字段、方法体零 Locator 构造；运行时参数化走具名工厂。元素清单可与前端 testid 清单逐行对照评审。

组件层（设计系统映射）

testid 打在组件宿主、真实控件在内部时，"宿主 → 内部"映射收口在 components/——组件库内部结构变化只改一处。

多角色同会话切换

maker 建仓 → checker 审批在同一浏览器会话完成（清 cookie 重登），业务产物经场景级上下文跨角色流转，无需双会话开销。

API 造数 + 测试粒度哲学

"E2E 是套件级属性"：审批用例经 API 造数隔离被测行为，失败即定位；API/UI 造数等价性用一条 @journey 全链路冒烟封口，不为对称堆用例。

工程化与稳定性策略

dotenvx 分环境注入（密钥不进库）；flaky 用例显形（报告标黄）→ --repeat-each 复现 → 修根因 → @flaky 隔离区不阻塞合并。

AI 工具链就绪

仓库已内置 Playwright Test Agents 脚手架（planner / generator / healer）——用例规划、生成与自愈的官方 AI 能力目前只在 Node 侧演进。

报告即文档：业务可读的用例长什么样

Scenario: TRADE-103 - Checker approves a pending trade from the trade details page
  Given a "FX_TRF" trade has been created via api          # API 造数，不占浏览器
  When the checker approves the trade from the trade details page
  Then the trade is approved and marked as new             # 封闭短语，列值在实现层

测试报告直接呈现这份文本——BA 不看代码就能复述每条用例在验证什么，这是 BDD 层带来的核心收益，也是后文评估"要不要为它承担维护风险"的天平另一端。

02 · 方案对比

三个候选：本框架 · genie-playwright（Java）· Python

Playwright 官方提供多语言绑定，但 Playwright Test runner 只存在于 Node.js 侧——fixtures 依赖注入、自动并行分片、UI Mode、watch、组件测试与 Test Agents 都是 runner 的能力而非绑定的能力。Java/Python 方案本质是"Playwright 浏览器驱动 + 各自生态的 runner"。这是对比的主轴。

对 genie-playwright 的公平结论

genie 的优势集中在集成面（报告、流水线、合规、内部支持团队），这些可以通过标准报告格式桥接部分获得；它的短板集中在 runner 面（Java 绑定无 Playwright Test，sync API 且实例非线程安全，并行与调试体验需生态自建），而 runner 能力无法桥接。对于一个被测系统本身是 TS 前端的项目，同语言协作 + 旗舰 runner 的组合收益大于生态迁移成本——若未来出现被测系统为 Java 服务端为主、或团队完全无 TS 技能的项目，genie 仍是合理默认。

03 · 风险专题

playwright-bdd 是个人维护的，停更了怎么办？

正面回答：这个风险是真实的，我们没有回避它，而是把它架构化了——耦合面被压缩到 21%，退出路径不是纸面方案而是一个持续维护的镜像分支。

先看事实

  • playwright-bdd 由单一核心维护者开发（社区活跃、迭代至 9.x），定位是构建期代码生成器：bddgen 把 .feature 编译成标准 Playwright Test spec，运行时没有它的存在——跑起来的就是纯 Playwright 测试。
  • 它是 devDependency：锁定版本后配合锁定的 Playwright 大版本可长期稳定使用。真正的风险窗口是"Playwright 出破坏性大版本升级 × playwright-bdd 已停更"两个条件同时成立。
  • MIT 协议，代码生成器体量可 fork 自维护（下策，但存在）。

依赖面：一张图

框架无关（POM / API / 数据 / 配置）— 1 946 行 · 79% playwright-bdd 耦合面（features / steps / fixtures）— 511 行 · 21%

全仓只有 8 个文件 import 到 playwright-bdd，全部位于接线层。承载真正复杂度的页面模型、业务流程、数据索引、API 造数——占代码量近八成——不知道 BDD 层的存在。

三层对冲，逐级兜底

锁版本继续用（零成本）

构建期工具停更不影响既有版本工作。只要不激进追 Playwright 大版本，现状可稳定运行以年计。

架构薄耦合（已内建）

steps 层被刻意约束为"短语 → 流程调用"的接线，不写逻辑；所有断言与操作在 pom/flows 层。替换 BDD 层不触碰任何业务建模代码。

实证退出路径（已演练）

仓库维护着 feature/plain-playwright 镜像分支：同一套 POM / 数据 / API 层，用原生 test.step 实现同样的用例。迁移不是估算出来的，是做过一遍量出来的——改写的就是那 ~500 行接线层。

迁移成本明细（若触发退出）

层代码量迁移动作

04 · 决策与下一步

请求确认的事项与推进节奏

  1. 确认选型：Trade Portal E2E 采用本框架（TS + Playwright Test + playwright-bdd 薄层），genie-playwright 继续作为 Java 侧项目默认。
  2. 真机首跑：当前为静态验证全绿（编译 / lint / 用例枚举），接入测试环境完成浏览器实跑与断言校准（如详情页确认后的跳转行为、状态列值）。
  3. 报告桥接：输出 JUnit XML / Allure 兼容格式接入内部报告平台，弥合与 genie 生态的集成差距。
  4. ADO 打通：caseId（TRADE-001 式编号）按设计机械替换为 work item ID，用例与需求双向可追溯。
  5. CI 接入：利用 runner 原生分片并行；@flaky 隔离区不阻塞主流程。
  6. 保险维持：plain-playwright 镜像分支随主干低频同步，作为 BDD 层的常备退出路径。
数据口径：代码行数与依赖面统计自仓库当前主干（features / src 实测，不含生成物与 node_modules）。对 genie-playwright 的描述基于 Playwright Java 绑定的公开事实与内部生态的一般特征，具体能力以内部文档为准。
