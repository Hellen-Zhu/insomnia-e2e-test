Technical Selection Report · Trade Portal E2E

E2E Automation Framework: Capabilities, Three-Way Comparison, and Risk Hedging

The trade-portal E2E framework built on Playwright Test (TypeScript) + playwright-bdd is up and running: all 14 test cases pass locally against the real application. This report summarizes what the framework can do, compares it with the other Playwright stacks the company maintains — the Java genie suite our team uses today and the pytest-based Python variant — and answers the playwright-bdd maintenance-risk question head-on.

Conclusion first

The one-line recommendation

Use TypeScript + Playwright Test for Trade Portal E2E: same language as the frontend under test, exclusive access to the official flagship runner (fixture DI, automatic parallelism, traces, UI Mode) and to the AI tooling roadmap; the BDD layer (playwright-bdd) comes in as a pluggable thin layer, its maintenance risk hedged by architectural isolation and a field-tested exit path.

What we recommend
TS + Playwright Test

The officially first-class language binding with the fullest runner; BDD is an optional thin layer that decouples business language from implementation.

Why not the other two
Engine and runner gap

The genie wrapper integrates Playwright but not its auto-waiting — waits are hand-written and hand-maintained in test code — and it parallelizes by forking JVMs. Its integration advantages can be bridged via reports — the company's own TS + genie report variant already proves that bridge; the engine and runner gap cannot.

Biggest risk
playwright-bdd is solo-maintained

The coupling surface is only 21% of the code, and a BDD-free mirror branch proves the exit path — the risk is quantified and reversible.

ROI at a glance
The build cost is already sunk — what you are approving is the marginal cost

The whole framework took one engineer 6 calendar days (git history, 55 commits). From here, a test case built from the existing vocabulary costs Gherkin lines plus a YAML block — the end-to-end journey smoke was added with zero new step definitions. Details and the honest cost side in section 04.

Eight core capabilities

Business-language discipline (six-rule vocabulary)

Business states are closed phrases, not parameters (e.g. the trade is approved and marked as new — verdict × status locked in two dimensions); off-vocabulary wording fails compilation outright, so the vocabulary cannot drift silently. Codified in docs/gherkin-style.md.

Three-tier data-driven design

caseIds in scenario titles bind YAML cases; a lazily built global index with namespaces (cases / *_preset) fails the build on duplicate keys and typos across files; deep-copied reads keep parallel workers safe. caseIds can later be swapped mechanically for ADO work item IDs.

POM discipline: Locator containment

Fixed elements are readonly class-head fields — zero Locator construction in method bodies; runtime parameterization goes through named factories. The element inventory can be reviewed line-by-line against the frontend testid list.

Component layer (design-system mapping)

When the testid sits on a component host and the real control lives inside, the host → internals mapping is contained in components/ — internal component-library changes touch exactly one place.

Multi-role switching in one session

Maker creates → checker approves within a single browser session (clear cookies, re-login); business artifacts flow across roles through a scenario-scoped context — no dual-session overhead.

API seeding + test-granularity philosophy

"E2E is a suite-level property": approval cases isolate the behavior under test via API seeding, so a failure localizes itself; the API/UI seeding equivalence gap is sealed by a single @journey end-to-end smoke rather than a padded matrix.

Engineering and stability practices

Per-environment env injection (secrets never enter the repo); flaky cases surface in reports (flagged yellow) → reproduce with --repeat-each → fix the root cause → quarantine under @flaky without blocking merges.

AI-toolchain ready

The repo ships the Playwright Test Agents scaffold (planner / generator / healer) — the official AI capabilities for test planning, generation, and self-healing currently evolve on the Node side only.

02 · Comparison

The real landscape: the company already runs three Playwright stacks

This is not a proposal to introduce Playwright — the company already maintains three Playwright variants: the full genie suite on Java (genie_playwright) — the stack our team uses today; the pytest-based Python stack (Playwright library + pytest + genie report, without the Playwright Test runner); and a TS Playwright + genie report variant. The proposal on the table is to move this team's new E2E work from the Java stack onto the TS base. Two consequences follow: choosing TypeScript here is convergence with an existing internal direction, not a fourth island; and the genie report bridge on the Node side already has an in-company precedent we can reuse. What this framework adds on top of that TS base is the business-language layer, the POM architecture, and the AI toolchain.

The comparison axis: the Playwright Test runner exists only on the Node.js side — fixture DI, automatic parallel sharding, UI Mode, watch, component testing, and Test Agents are runner capabilities, not binding capabilities. The Java and Python stacks pair the Playwright browser driver with their own ecosystem's runner.

A fair verdict on genie-playwright

genie's advantages concentrate on the integration surface (built-in Cucumber-JVM, reports, pipelines, compliance, an internal support team) — partially attainable through standard report formats; its weaknesses concentrate on the engine and runner surface — engine auto-waiting is not integrated, so stability must be piled up with hand-written explicit waits (a per-test maintenance bill, measured by comparison 2); parallelism forks JVMs with linearly growing overhead; and there is no Playwright Test fixtures or trace experience — none of which can be bridged. For a system whose frontend is itself TypeScript, same-language collaboration plus the flagship runner outweighs the ecosystem-migration cost; for Java-dominated projects or teams with no TS skills, genie remains the sensible default.

The second decision: how to layer BDD on the Node side

Settling on TypeScript leaves one more choice: plain Playwright (no BDD), Cucumber.js driving Playwright, or playwright-bdd. One thing is not at stake — auto-waiting is an engine capability and survives all three. The real trade is between the runner and Gherkin.

These three are not three strangers competing — they are one choice and its two exits. playwright-bdd is the only option that keeps both the full runner and Gherkin; its price is the solo-maintainer risk, priced in section 05. Plain Playwright keeps the runner but locks business readers out; Cucumber.js keeps Gherkin but surrenders the very runner that decided the language comparison above. Both alternatives remain reachable from the same ~500-line glue — one lives as a maintained mirror branch, the other shares Gherkin text and expression syntax verbatim — and they are precisely rungs 3 and 4 of the exit ladder in section 05.

Where the time comes back

  • Maintenance — the waiting layer is engine-native and officially maintained: a whole class of sleep-tuning flakiness never enters the codebase, whereas on the current Java stack every wait is hand-written and hand-maintained, one test at a time (sections 02–03); the trace viewer turns "cannot reproduce" into a recording with per-step DOM snapshots, so triage becomes watching a replay instead of re-running.
  • Shift-left (the biggest lever) — the story TDD toolchain drafts BDD features from the user story before development starts; QA's role moves from authoring from scratch to reviewing a draft. Same headcount, earlier coverage — and it runs natively on the Node toolchain today.
  • Execution — dynamic per-test scheduling plus browser reuse means regression wall-time scales down with worker count, without paying a JVM warm-up per fork (section 02).

The levers are stated qualitatively on purpose — the numbers get back-filled from the first real iteration, the same treatment as the four placeholders in section 03. We would rather show two measured numbers later than four invented ones today.

The honest cost side — what we are not counting as free

  • Learning curve (estimate) — case authors never touch TypeScript: adding cases is Gherkin plus YAML. Framework maintainers do; for a Java-background engineer, expect 1–2 weeks to productivity (estimate, labelled as such).
  • The legacy suite — no big-bang migration is proposed. New modules start here; the existing Java suite keeps running and migrates per module only when touched. The migration bill is paid in instalments, and each instalment is optional.
  • AI review time — generated designs are not free coverage: every draft passes a human gate (the AC coverage table) before implementation. Review time is a real cost — it is simply smaller than authoring from scratch.
05 · Risk deep-dive

playwright-bdd is solo-maintained — what if it goes unmaintained?

Answering head-on: the risk is real. We did not sidestep it — we architected it away: the coupling surface is squeezed to 21%, and the exit path is not a paper plan but a continuously maintained mirror branch.

The facts first

  • playwright-bdd is built by a single core maintainer (active community, iterated to 9.x) and is a build-time code generator: bddgen compiles .feature files into standard Playwright Test specs — it does not exist at runtime; what runs is pure Playwright tests.
  • Adoption (measured 2026-07, npm registry): 342k installs per week, roughly 4× year-over-year growth; 3 releases in the last six weeks (9.0.0 → 9.2.0). Already 15% of cucumber-js volume — a project on the way up, not on the brink of abandonment. (Caveat: weekly downloads are dominated by CI reinstalls — a scale proxy, not a user count.)
  • It is a devDependency: with pinned versions alongside a pinned Playwright major, it runs stably for years. The real risk window requires two conditions at once: "Playwright ships a breaking major" × "playwright-bdd is already unmaintained".
  • MIT-licensed, and small enough to fork and self-maintain — the intermediate rung before any exit: our usage surface is just 8 items, and a build-time tool fails loudly (compilation breaks immediately; no silent runtime corruption), which keeps self-maintenance risk contained.

The dependency surface in one picture

Framework-agnostic (POM / API / data / config) — 1,946 LOC · 79% playwright-bdd coupling surface (features / steps / fixtures) — 511 LOC · 21%

Only 8 files in the whole repo import playwright-bdd, all in the wiring layer. The page models, business flows, data index, and API seeding that carry the real complexity — nearly 80% of the code — do not know the BDD layer exists.

Three hedges, escalating

Pin versions and keep going (zero cost)

An unmaintained build-time tool does not stop existing versions from working. As long as we do not chase Playwright majors aggressively, the status quo runs for years.

Thin coupling by architecture (already built in)

The steps layer is deliberately constrained to "phrase → flow call" wiring with no logic; all assertions and actions live in the POM/flows layers. Replacing the BDD layer touches no business modeling code.

A field-tested exit path (already rehearsed)

The repo maintains a feature/plain-playwright mirror branch: the same POM / data / API layers implementing the same cases with native test.step. The migration cost is not an estimate — it was measured by doing it once: what gets rewritten is that ~500-line wiring layer.

The alternative — Cucumber.js (SmartBear's official JS implementation) — would preserve Gherkin but abandon the Playwright Test runner, which is precisely why we chose this stack; hence it ranks last.

06 · Decision and next steps

What we ask you to confirm, and the rollout rhythm

  1. Confirm the selection: Trade Portal E2E adopts this framework (TS + Playwright Test + a thin playwright-bdd layer); genie-playwright remains the default for Java-side projects.
