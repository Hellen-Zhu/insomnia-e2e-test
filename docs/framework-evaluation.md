# 评估一个 E2E 自动化框架需要看哪些方面

评估维度与本框架（`e2e-framework`）现状的对照。

## 1. 架构设计：分层是否清晰、边界是否可强制

- **职责分层**：UI 建模层（page/component/flow）、接线层（fixtures/steps）、基础设施层
  （api/config/utils）是否物理隔离，边界能不能靠 lint 规则强制（而不是靠自觉）
- **依赖方向**：高层能不能反向依赖低层？低层有没有意外耦合业务细节？
- **fixture/依赖注入设计**：能不能按最小公共祖先声明依赖，避免每个测试都要拼一遍
  所有能力

→ 已有 `src/pom/{pages,components,flows}` 唯一持有 Locator、fixture 继承树
（base → tradePortal → {trade, product}）——**已具备**，唯独 `no-restricted-imports`
的 eslint 强制还没配，目前靠约定。

## 2. 测试设计质量：数据驱动、场景组织

- caseId/数据溯源：能否从报告一路找回是哪条业务数据触发的失败
- Outline 使用是否恰当：差异轴是否业务可见，是否为了"看起来复用"而牺牲可读性
- presets vs cases 边界：前置条件和被测行为的数据是否混在一起
- **覆盖率是否对应真实业务价值**，而不是"凑够看起来完整的矩阵"

→ 这几周反复打磨的就是这一层——目前投入最多、也最扎实的部分。

## 3. 稳定性（anti-flakiness）：自动化框架能不能被信任的核心

- 等待策略：显式等待 vs 固定 sleep vs 网络响应拦截
- 测试隔离：并行 worker 之间是否有共享可变状态（读写 YAML、共享登录会话等）
- retry/flaky 治理流程：有没有区分"重试后通过"和"稳定通过"，有没有隔离 `@flaky`
  的机制

→ 并行安全性已专门评估过（只读 YAML + structuredClone + 进程隔离）；README 里也
写了 flaky 治理四步。设计到位，但**从未真机验证过**——浏览器至今没装，这是个悬而
未决的风险点。

## 4. 可维护性：换人接手的成本

- 命名规则一致性（testid 命名不一致已在收集反馈清单）
- 新增一个用例/一个页面的改动面有多大——理想情况应该"只加数据/配置，不改代码"
- 文档与代码是否会自然漂移

→ 已验证过好几次"新增 case = 加 YAML + 加场景，代码零改动"，这是可维护性最直接
的证据。

## 5. 执行效率：能不能在 CI 里快速给出反馈

- 并行化程度、sharding 策略
- 该用 API 造数的地方有没有还在走 UI（前置用 `tradeApi`、被测才走真实 UI，已区分）
- 整体套件的执行时间预算——多少分钟内必须出结果

→ 造数分层已经做了，但**还没有真实的执行时间数据**，因为从没跑过完整套件。

## 6. CI/CD 集成与可观测性

- 能不能接流水线做 PR 门禁
- 失败时能不能自助定位（trace、截图、`ctx` 快照）而不需要人工复现
- 报告是否可追溯到业务侧（ADO Test Plan 映射——caseId 格式已在设计层面预留）

→ 目前是空白项——还没有 CI 配置、没有真实报告产出过。这是这套框架"设计完整度"和
"运行验证度"之间目前最大的落差。

## 7. 团队协作与治理

- 代码评审能否覆盖测试代码（测试代码是不是"二等代码"）
- 是否有明确的"谁负责维护哪一块"的边界
- 新人上手成本——文档、示例场景是否足够

## 两条容易忽略的判断准则

- **"设计得多好"和"跑起来有多稳"是两件独立的事**，前者靠架构评审，后者只能靠
  真实执行数据（通过率、耗时、flaky 率）去验证。本框架目前在第一件事上投入扎实
  （分层、数据驱动、并行安全性都推演过好几轮），但因为浏览器从未装、套件从未真跑
  过，第二件事完全是空白——这不是设计缺陷，而是"验证阶段尚未开始"的正常状态，
  评估时不要把两者混为一谈。
- **框架与团队现状的匹配度**：一个技术上完美的框架，如果团队里没人能维护，价值会
  打折扣。评估框架时问"三个月后离开这个项目，新人接手需要多久能改一个用例"，往往
  比问"架构图画得多漂亮"更接近真实价值。
