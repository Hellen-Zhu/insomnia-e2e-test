一 · 开场白

两个版本，按老大风格选

标准版 · 约 60 秒 "占用大家十五分钟，汇报 trade portal E2E 自动化的选型。先说结论：我建议用 TypeScript 加 Playwright Test，BDD 作为可选的薄层。这个结论有三个支撑——第一，框架不是方案设想，已经落地 14 条用例、两千四百多行代码，并且全部在本地实跑通过；第二，公司现在同时维护三个 Playwright 版本——我们在用的 Java 全套 genie、Python 加 genie report 的版本、还有一个 TS 加 genie report——选 TS 是靠拢已有方向，不是另立山头；和我们现用的 genie 逐项对比，最关键的差异有两个：genie 集成了 Playwright 但没有集成它的自动等待，等待要在用例里手写、自己维护，我们这边是引擎原生、微软官方维护；并行只能 fork JVM，开销随并行度线性涨——这两条都有实测数据；第三，选型里最大的风险点——BDD 那一层是个人维护的开源项目——我没有回避，是用架构手段对冲掉的，后面有专门一节。下面按这个顺序展开。"
极简版 · 20 秒 "结论：trade portal E2E 用 TS + Playwright Test，14 条用例已经本地全部跑通。今天讲三件事——它能做什么、为什么不是 genie 或 Python、playwright-bdd 个人维护的风险怎么兜底。"
先把风险自己说出来。"playwright-bdd 是个人维护的"由你先讲，性质是"我做过风险管理"；等老大先问出来，性质就变成"你没想到"。

各节展示动作

  • 框架能力：四个数字条读一遍；架构图手指右侧括号——"注意这个 79/21，是风险节的伏笔"（埋钩子）；Gherkin 示例读一遍那三行英文——"报告直接长这样，BA 不看代码能复述这条用例在验证什么"。八张能力卡只点一两张，其余"细节文档里有"。
  • 对比表：不逐行读。先讲主轴（Playwright Test runner 只在 Node 侧），先指 genie 列的绿色格子："这两格是 genie 真实的优势，我标的绿"——先替对方说出它的好，你的结论才有公信力。再停在"等待机制"那行，一句话："genie 集成了 Playwright，但自动等待没带进来——等待散在用例里手写手维护；我们这套是引擎原生、微软维护，这笔维护账不用付。下一节有实测数字。"收在"Java 项目 genie 仍是合理默认"。
  • BDD 三选一：先指自动等待那一行——"三条路全绿，引擎能力，这个决策动不到它"——把战场收窄到 runner 和 Gherkin 两样。再指 playwright-bdd 列："唯一两样都保住的"，代价（个人维护）直接预告第 5 节。最后一行"离本仓库的距离"是彩蛋：镜像分支 = 原生路线已演练，Cucumber = 文本逐字兼容——对手即退路。
  • 实测对比：四组图各一句话，重心放对比 1（并行折线张口）和对比 2（显式等待 N 处 vs 0 处）。对比 4 若时间允许现场演示 trace viewer——打开的瞬间效果好于任何静态图。
  • ROI：先把四个数字条读一遍（6 天 / 2.3 倍复用 / 0 新增步骤 / 1 段 YAML），强调"全部是仓库里量出来的，git 可查"。三档成本表指着第三档说："真正花工时的只有开新页面这一档——每个框架都要付，而且每页付一次，不是每条用例付一次。"回报杠杆不逐条展开，收在一句："杠杆我刻意没写数字，等第一个迭代实测回填——宁可晚点给两个真数，不今天给四个编的。"这句和能力节的"从宽标注"、风险节的"量出来的退出路径"是同一个信誉策略，老大会认。
  • 风险专题：节奏放慢。顺序：事实（构建期代码生成器，运行时不存在）→ 条形图 → 三层阶梯 → 迁移成本表。最硬的一句留在最后："迁移成本不是我估算的——我们真的维护着一个不用 BDD 的镜像分支，同样的用例原生写法实现了一遍。"
三 · 分节讲稿（照读版）

每节一段，可直接读

02 框架能力 · 约 90 秒 "这一节证明一件事：这不是方案设想，是已经落地的框架。四个数字——14 条用例本地全部实跑通过、两千四百多行框架代码、28 个页面模型文件、两个分支并行维护。架构一句话：业务语言到页面细节是单向依赖；右边这个 79 比 21，是后面风险节的伏笔。往下这张能力对照总表是给您省时间的：上半区是对齐区——genie 支持的，BDD 用例组织、数据驱动、并行、重试、多环境切换、API 造数、数据库落地验证、报告、多浏览器——我们逐项都有；而且 genie 侧我是从宽标注的，没逐条核实的都按它有算，即便如此结论也不变。下半区是增量区——自动等待与 web-first 断言（genie 集成了 Playwright 但没有集成这个，等待要在用例里手写）、worker 级并行、UI 调试模式、步骤编译期检查、AI 测试工装链——这些 genie 不具备，我们已经落地。这张表一句话总结：genie 有的都有，genie 没有的也有。"
03 三方案对比 · 约 2 分钟 "对比之前先讲一个背景：公司现在同时维护三个 Playwright 版本——Java 侧全套 genie，我们现在用的就是这套；Python 侧 pytest 加 Playwright 库加 genie report，没有用到 Playwright 官方 runner；还有一个 TS Playwright 加 genie report。所以今天的提案是把我们团队新项目的 E2E 从 Java 栈挪到 TS 基座上——不是引入第四个孤岛，是靠拢公司已有的 TS 方向：同一个基座，加上业务语言层和 AI 工装链，genie report 的对接直接复用 TS 版的先例。对比的主轴一句话：Playwright 官方的 Test runner 只存在于 Node 侧——Java 和 Python 拿到的是浏览器驱动加各自生态的 runner，不是完整测试平台。先说 genie 真实的优势，这两格我特意标了绿色：Cucumber-JVM 官方维护、生态最成熟；genie 全家桶的报告和流水线开箱即用。这些是真优势，我不回避。但请看等待机制这一行：genie 集成了 Playwright，但没有集成它的自动等待——用 genie 拿到的是 genie 自己的特性集，等待得在用例里手写、自己维护；我们这边是引擎原生、微软官方维护，这笔维护账不用我们付。两种写法在用例层的差距，下一节有实测数字。我的结论保持克制：Java 项目 genie 仍是合理默认；但 trade portal 是 TS 前端项目，匹配度在我们这边。"
03b BDD 三选一 · 约 60 秒 "语言定了是 TS 之后，还有第二个决策：BDD 这层怎么叠。桌上三条路——原生 Playwright 不要 BDD、Cucumber.js 当 runner 驱动 Playwright、我们选的 playwright-bdd。先划掉一个干扰项：三条路的自动等待都在，那是引擎能力，这个决策动不到它。真正的取舍在两样东西上：runner 和 Gherkin。原生路线保住全部 runner 能力，但业务同事读不了用例；Cucumber.js 路线 Gherkin 是官方正统，但 runner 换成了 Cucumber 自己的——fixtures、动态并行、trace、UI Mode，刚才对比节讲的优势就让出去了；playwright-bdd 是构建期代码生成器，生成的就是原生 Playwright 用例——runner 和 Gherkin 两样都保住，代价是它是个人维护的项目，这个风险第 5 节专门定价。最后点破一层关系：这三条路不是三个陌生候选，另外两条正是我们退出阶梯的第三、四级——原生写法我们真的维护着镜像分支，Cucumber 用的是同一套 Gherkin 文本和步骤匹配语法。选 playwright-bdd 不是压注，是三条路里唯一全都要的那条，而且两条退路都已经量过距离。"
04 实测数据 · 约 60 秒 "上一页是能力表，这一页是数字，四组对比用的是同一条业务用例。重点看两组：第一组，并行扩展——worker 数从 1 到 2 到 4，两边的耗时曲线【照图读数字】；第二组，显式等待密度——同一条用例 genie 侧写了【N】处显式等待，我们是零处——这就是差距在用例层的直接体现：一边散在用例里手写手维护，一边是引擎原生。第四组是失败诊断：同一个失败，我们这边拿到的是 trace——可以时间旅行回放的现场【条件允许当场打开】。"
05 ROI · 约 2 分钟 "这一节直接回答投入产出的问题，先说结论：建设成本已经沉没，今天要批的是边际成本。投入面——整套框架是一个人、六个自然日建完的，55 次提交，git 历史可查，这笔钱已经花完了，不在审批范围内。边际成本我不是估的，是从仓库里量出来的三个数字：第一，目前 15 个步骤定义支撑了 34 处场景引用，复用 2.3 倍，且随规模只升不降；第二，全链路 journey 冒烟那条用例，新增步骤定义是零——完全用已有词汇拼出来的；第三，同形状的数据变体，成本是一段 YAML，一行 TypeScript 都不用写。所以加一条用例分三档：词汇够用的，分钟级；缺步骤的，每步一行胶水，编译器自动列缺口清单；真正花工时的只有开新页面这一档——而这一档每个框架都要付，且每页只付一次。回报在三处：维护上，自动等待砍掉了调 sleep 这一整类排障，trace 把'复现不了'变成看回放；最大的杠杆是前移——开发还没动工，AI 工装链已经从 user story 产出用例草稿，QA 从'从零写'变成'review'；执行上并行随 worker 数横向扩。这些杠杆我刻意没写数字，第一个真实迭代跑完用实测回填。成本面我也照实列了：维护框架的人要一到两周上手 TS——这是估算，文档里我标了估算；存量 Java 套件不搞大爆炸迁移，新模块走新框架，碰到再迁、分期付款，每一期都可以不付。"
06 风险专题 · 约 2 分钟（放慢） "这一节回答今天最尖锐的问题：playwright-bdd 是个人维护的开源项目，停更了怎么办。第一，先看事实：它是构建期的代码生成器，生成的是标准 Playwright 测试，运行时它不存在——锁定版本可以稳定使用以年计，不存在'跑着跑着坏了'。第二，看这个条形图：架构上把耦合面压到了 21%，绿色这 79% 的代码根本不知道它存在。第三，退出路径——这句话请允许我强调：迁移成本不是我估算的，是做过一遍量出来的。我们真的维护着一个不用 BDD 的镜像分支，同样的用例、原生写法、完整实现了一遍。真要退出，改的就是那五百行接线层，其余原样保留。"
07 下一步 · 约 30 秒 "下一步五件事，但今天请您确认的只有第一条：选型本身。其余四条——接共享测试环境、CI 分片并行、报告平台对接、核心回归铺开——都是选型确认之后的执行项，不需要今天拍板。"
四 · Q&A 预案

按被问概率排序

Q1 · 公司有 genie，为什么另起炉灶？必问

"不是对 genie 的否定，是匹配度问题。genie 给我们的是集成面——Cucumber、报告、流水线，这些可以桥接回去，公司 TS 加 genie report 的版本已经证明这条路通，下一步计划里有这条。但两个引擎级差距桥不过去：一是等待层——genie 集成了 Playwright 但没有集成它的自动等待，稳定性要靠显式等待在用例里一处一处堆、自己维护，我们这边是引擎原生、微软官方维护，实测第 2 组直接量这个差距；二是并行靠 fork JVM，进程启动和内存开销随并行度线性涨。我们被测系统本身是 TS 前端，同语言意味着前端同事能直接读懂甚至贡献页面模型。Java 项目我仍然建议默认 genie。"

答案里必须出现"genie 仍是 Java 项目的默认"——姿态是补位不是替代。有实测数据时直接翻到实测对比节。
Q1b · 你们的 worker 不也是进程吗？和 fork JVM 有什么本质区别？可能

"对，Playwright 的并行也是进程模型，这点和 fork JVM 一样——差别在三处。一是每个进程的重量：Node worker 几十兆、毫秒级启动；JVM 每次 fork 数百兆、秒级启动，还要重新 JIT 预热，并行度越高线性差距越大。二是调度：Playwright runner 是用例级动态调度，worker 空了就取下一条，失败重试派到新 worker；fork JVM 是开跑前静态切块，先跑完的等最慢的。三是浏览器复用是设计内建的：worker 里浏览器跨用例复用，每条用例只开一个毫秒级的 context 做 cookie/storage 隔离——贵的资源复用、需要隔离的资源轻量新建，两层是拆开的；fork JVM 模型里这两层绑在一起，每个并行单位都要付全套。至于协程——那是用例内部的 async I/O，管的是单条用例里并发发请求（比如同时造三笔数据），不是并行机制本身。另外补一句：Playwright 的 Java 实例本身非线程安全、API 是同步阻塞的，想用线程代替进程并行会踩雷——这正是 genie 只能 fork JVM 的原因。"

这题是 Q1 里 fork-JVM 论点被反问时的续篇。先承认"都是进程"再展开三个维度——不承认这一点，后面说什么都像诡辩；承认了，反问反而成了展开真正差异的跳板。
Q1c · 公司已经有 TS Playwright 加 genie report 的版本了，你这套和它什么关系？大概率

"是同一个方向，不是竞争关系。那个版本证明了两件事：TS Playwright 这条路线公司内部已经走通，genie report 在 Node 侧的对接是现成的——我下一步的报告对接就是直接复用这个先例，是照抄不是攻关。我这套在同样的 TS 基座上多加了三层：业务语言层，BA 不看代码能读懂用例在验证什么；页面对象架构，locator 全部收口在一个子树里，UI 改版只动一处；AI 工装链，story 还没开发就能出用例草稿。一句话：不是第四个孤岛，是在公司已有的 TS 方向上加了工程化和 AI 这两级。"

这张卡和 Q1 是一对：Q1 答"为什么不是 Java genie"，这张答"为什么不直接用现成 TS 版"。核心词是靠拢和先例——把"另起炉灶"的指控拆掉。
Q1d · 我们现在用的就是 Java genie，迁移成本怎么算？必问

"这次决策里没有迁移这一项。trade portal 是新项目，E2E 反正要从零建模——选型决定的是新资产长在哪个栈上，不是要不要搬旧资产。存量 Java 套件继续跑，将来碰到哪个模块才迁哪个，分期付款，每一期都可以不付。团队技能上，用例作者不碰 TS——写的是业务语句加 YAML；需要 TS 的是框架维护这个角色，Java 背景一到两周上手，这是估算、文档里标了估算。所以迁移成本这笔账，今天只有'新东西用什么写'，没有'旧东西要重写'。"

这题的陷阱是让"换框架"听成"重写一切"。核心动作是把决策缩小到增量资产：新项目、零存量、随时可停。别贬低 genie 那套——团队自己天天在用，贬它等于贬自己人；如果平时踩过手写等待、fork JVM 慢这些具体的痛，加一个真实例子比任何论证都硬。
Q2 · playwright-bdd 停更了怎么办？必问

"先给个规模感：npm 周安装 34 万次、一年增长约 4 倍、近六周发了三个版本——它在上升期，不在弃养边缘。但我们的兜底不赌这个。三层：第一层，它是构建期的代码生成器，跑起来的就是纯 Playwright 测试，锁定版本可以稳定用以年计；第二层，架构上耦合面压到了 21%，八成的代码不知道它存在；第三层是实证——我们维护着一个不用它的镜像分支，同样的用例原生写法跑通了，真要退出，改的就是五百行接线层。"

Q2b · 除了退回原生，还有别的退路吗？能不能我们自己维护它？可能

"有，退路完整说是一个四级阶梯，一级比一级动作大。第一级，版本锁定——它是构建期工具，锁住版本可以稳定用以年计，期间什么都不用做。第二级，fork 自维护——它是 MIT 协议的 TypeScript 项目，法律上随意 fork；关键是我们要维护的面很窄：全仓对它的使用清单只有八项，真正脆弱的只有它对 Playwright 内部配置加载的兼容层，Playwright 大版本升级时可能要补一次，量级是天不是月。而且它是构建期工具，坏了编译立刻红，不存在运行时静默出错——自维护一个'坏了会大声喊'的工具，风险可控。第三级，退到 Cucumber.js——SmartBear 官方维护：Gherkin 文本逐字保留、步骤匹配串原样搬（两边用的是同一套 cucumber-expressions），丢的是 Playwright runner 的 fixtures 和调试集成；自动等待不丢，它是引擎能力不是 runner 能力。第四级，退回原生 Playwright——保住全部 runner 能力，Gherkin 降级为 step 标题，这条已经用镜像分支演练过。四级动的都是同一份五百行接线层，79% 的代码在任何一级都原样不动。选哪级，取决于当时为什么要退。"

fork 选项主动讲会加分——它把"个人维护"从威胁翻转成"最坏情况我们接得住"。两个必须点到的词：MIT（法律干净）、构建期失败是响的（自维护安全的根据）。Cucumber 一问参见此卡第三级，不必单独展开代价细节：代码面与原生退路同量级（~500 行），只是保留/丢弃的东西相反。
Q3 · genie 底层不也是 Playwright？你说的差距从哪来？大概率

"底层是同一个浏览器驱动，但 genie 的封装层没有把引擎的自动等待带出来，web-first 断言也没有对应物——用 genie 拿到的是 genie 自己的特性集。等待就得散在用例里手写：动画、元素替换、异步渲染这些边角场景全要自己兜，页面一改版还要一处处修。实测对比第 2 组直接数的就是这个：同一条用例，genie 侧要写 N 处显式等待，我们是零。"

这题是送分题，把话题引向实测对比节。
Q3b · AI agent 那套，给 genie 也配一套不就行了？大概率

"理论上可以，我拆开说。agent 体系分三层：规则和设计那一层是纯文本，Java 项目完全可以用；浏览器探索层面向的是应用不是框架，也能用。卡住的是执行层——'跑测试、停在错误现场、检查页面、改代码、重跑'这个自动回路。微软把这套 harness 作为官方产品只随 Node 版发布，我们是改配置就用上了；Java 侧要自建等价物。而且就算建成，有两样东西拖累它：agent 的工作方式是高频'改一点跑一次'，genie 每次迭代都要付编译加 fork JVM 启动的成本，这个延迟对 agent 是乘法惩罚；更关键的是自动修复回路要求极低的 flaky 底噪——底噪取决于等待层，genie 侧等待靠用例里手写，底噪天然高；引擎原生等待把这层噪音直接消掉，不然 agent 分不清真回归和时序噪音。所以准确的说法不是 Java 做不到，而是：同样的投入，Node 侧的 agent 已经在干活，Java 侧还在造工具。"

这题是 Q3 的 agent 版本。主动承认"可以自建"，可信度反而上升——对照表里 genie 那格的备注就是这么写的，口径一致。
Q3c · Python 版 Playwright 呢？浏览器驱动不是官方的吗？可能

"浏览器驱动确实是官方的，但运行器不是——这是 Python 版和 TS 版最本质的差距。Python 版依赖 pytest 做测试运行器，pytest 很强大，但它是一个通用的第三方测试框架，跟 Playwright 是松耦合关系，功能靠插件拼。TS 版用的是 @playwright/test，Playwright 团队自己维护的原生运行器，这带来三层差距：配置上，一个 playwright.config.ts 文件就能管住浏览器、超时、重试、报告，pytest 侧要靠多个插件配合；功能上，分片并行、worker fixture、UI Mode 这些深度能力只有 TS 版有；版本节奏上，Playwright 出新功能，@playwright/test 第一时间跟上，pytest-playwright 插件永远慢半拍。IDE 集成上差距更直观：Playwright 官方 VS Code 插件只支持 TypeScript/JavaScript——测试侧边栏 Test Explorer 点一下就跑用例、打断点单步调试看变量、Codegen 点哪录哪自动生成脚本、Copilot 在 Playwright 上下文里推荐定位器和断言；Python 版在 VS Code 里只有基础语法高亮和补全，这些深度集成一样都没有。三个版本摆在一起规律是一致的：越靠近 Playwright 官方核心，TS 侧拿到的东西越完整。"

这题不必主动提，被问到再答——Python 不是今天决策的对手（决策是 Java 迁 TS），主动讲太多显得在贬另一个团队的技术选型。收尾那句"越靠近官方核心，TS 拿到的越完整"和 Q1c"靠拢公司已有 TS 方向"是同一个逻辑，可以顺手接回去。
Q4 · 跑过真机吗？效果如何？可能

"14 条用例本地已经全部跑通，今天可以现场跑一条给您看。下一步是接入共享测试环境和 CI 分片并行。"

如果现场条件允许，直接跑——一条用例 + trace viewer，比任何回答有力。
Q5 · 谁来维护？团队都是 Java 背景怎么办？可能

"框架把维护成本压在纪律上：Locator 只允许出现在 POM 层且有收口规则、业务措辞有六条规范约束、数据全走 YAML——写用例的人接触的表面积很小。TS 对 Java 背景的 QA 语法迁移成本不高，真正要学的是 Playwright 本身，这个成本三个方案是一样的——而且 genie 那套显式等待的写法学起来并不比 auto-wait 简单。"

需要你自备：团队里谁接、占多少人力（见第六节清单）。
Q6 · BDD 值不值？写用例会不会更慢？可能

"我们对这个问题做的不是判断而是实验：两个分支并行维护，同样的用例 BDD 写法和原生写法各一份。结论是写的速度差别不大，差别在读——Gherkin 报告 BA 能直接读。而且 BDD 是可选薄层，今天选了以后随时能退。"

Q7 · 镜像分支不是双倍维护成本吗？可能

"不是实时同步，是低频按需同步——POM、数据、API 层本来就共用，每次同步的只有接线层。它的定位是保险单，保费很低。"

Q8 · 怎么接我们的报告平台 / 流水线？可能

"Playwright 原生输出 JUnit XML，Allure 也有现成 reporter，接内部平台是一次性工作，在下一步计划第三条。"

Q9 · 万一 Playwright 本身不行了呢？可能

"Playwright 是微软维护的行业事实标准。而且这层风险和选 genie 完全一样——genie 底层也是 Playwright，这不是方案之间的差异项。"

关键是最后一句：把"Playwright 风险"从你的方案剥离，它是所有候选共担的。
Q10 · 多久能覆盖核心回归？可能

"建模成本已经量化：trade portal 91 条元素收敛成 28 个文件；复用已有步骤时新增一条用例就是几行 Gherkin。核心回归清单有 N 条，按此估算约 X 周。"

N 和 X 需要你会前定好（见第六节清单）——这题不能现场即兴。
五 · Demo 动线

六步动线：每个动作只证明一个论断

Demo 的结构原则：先照读论断，再动手，动完收一句——展示的不是功能，是汇报里各节论断的证据。全程 5–7 分钟，顺序即叙事：读用例 → 跑用例 → 看报告 → 看失败 → 看 AI → 收场。

步论断（先照读）动作收束句兜底
0 · 开场
30s		 "接下来五分钟，所有东西都是这个仓库里的真实代码，不是录屏。" VS Code 打开仓库，目录树停在根目录——和汇报页架构图对上 "目录就是汇报里那张分层图。" 纯静态，不会失败
1 · 读用例
1 min		 "BA 不看代码能复述这条用例在验证什么。" 打开 trade-approval.feature 照读三行；点开同 caseId 的 YAML 数据块 "报告里呈现的就是这段文本，用例和数据靠 caseId 对齐。" 纯静态，不会失败
2 · 跑用例
2 min		 "全仓零处显式等待，并行是 runner 原生的。" npm run test:smoke；等待时指终端讲 worker 数和自动等待 "X 条通过，用时 Y 秒——没有一行 sleep。" 预跑好的终端输出/上一份报告
3 · 看报告
1 min		 "一次运行出两份报告：工程师一份，业务一份。" 打开 Playwright HTML report，再切 Cucumber HTML "BA 看到的就是刚才读的那段业务语言。" 报告本来就是预生成的
4 · 看失败
2 min		 "失败不是一行报错，是可以回放的现场。"（全场最强瞬间） 切到后台预开的 trace viewer（预生成的失败 trace）；拖时间轴，点一步看 DOM 快照 + 网络请求 "排障从'找人复现半天'变成'看五分钟回放'。" trace 预生成即兜底；再退一步用汇报页静态图
5 · 看 AI
1 min		 "AI 工装链不是概念，是仓库里的文件。" ls .claude/agents .claude/skills；打开 bdd-designer 定义或 specs/ 里一个移交包 "story 还没开发，用例草稿已经能出来——QA 从从零写变成 review。" cat 文件不会失败
6 · 收场
30s		 —— 切回汇报页"下一步"章节 "demo 每一步对应汇报里的一节论断，可以回头对。今天请您确认的只有选型这一条。" ——
顺序可裁不可乱。时间被压缩就从后往前砍：先砍 5（AI 留给 Q&A 被问时再掏），再砍 3（报告一句话带过）。1 · 2 · 4 是最小可行 demo——读用例、跑用例、看失败，三步就撑得起全部核心论断。
任何一步出岔子，念兜底句切静态备份，绝不现场排查。台词："这个环境问题我会后看，先看预跑好的结果。"现场排查两分钟造成的伤害大于 demo 全砍。开始前：终端字号调大、系统通知关闭、无关标签页关掉。两种用法里推荐集中式（讲完"下一步"后完整走一遍，叙事不断）；若嵌入式，只保留第 4 步嵌在实测对比节。
六 · 会前清单

需要你自备的弹药

  • 实测对比四组数据：按文档第 03 节的固定口径跑出图表替换占位（对比 1 速度、对比 2 显式等待密度、对比 3 代码量、对比 4 失败产物）。最少先出 2——一个数字就能讲。
  • 现场演示预热：本地跑通一条建仓用例 + 预先生成一份失败 trace，trace viewer 提前打开放在后台标签页。
  • 人力安排：谁维护、占多少时间（Q5 的下半句）。
  • 核心回归规模估算：N 条用例、约 X 周（Q10 不能即兴）。
  • genie 补课：确认它有没有 TS 支持路线图、报告平台的接入格式要求——对比表任何一格被当场纠错都会伤害整份文档的可信度。
  • AI 工装链被追问时的展示：终端预开仓库，30 秒动作：ls .claude/agents .claude/skills + cat 一个 agent 定义——"这不是概念，是仓库里的文件"。
