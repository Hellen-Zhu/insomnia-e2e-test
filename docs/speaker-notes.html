E2E 选型汇报 · 讲稿与应答预案

配合《E2E 自动化框架选型汇报》使用。汇报总长 12–15 分钟 + 提问。

一 · 开场白

两个版本，按老大风格选

标准版 · 约 60 秒 "占用大家十五分钟，汇报 trade portal E2E 自动化的选型。先说结论：我建议用 TypeScript 加 Playwright Test，BDD 作为可选的薄层。这个结论有三个支撑——第一，框架不是方案设想，已经落地 14 条用例、两千四百多行代码，并且全部在本地实跑通过；第二，我拿它和内部的 genie-playwright、Python 方案做了逐项对比，最关键的差异有两个：genie 的封装不支持自动等待，稳定性要靠手写等待去堆；并行只能 fork JVM，开销随并行度线性涨——这两条都有实测数据；第三，选型里最大的风险点——BDD 那一层是个人维护的开源项目——我没有回避，是用架构手段对冲掉的，后面有专门一节。下面按这个顺序展开。"
极简版 · 20 秒 "结论：trade portal E2E 用 TS + Playwright Test，14 条用例已经本地全部跑通。今天讲三件事——它能做什么、为什么不是 genie 或 Python、playwright-bdd 个人维护的风险怎么兜底。"
先把风险自己说出来。"playwright-bdd 是个人维护的"由你先讲，性质是"我做过风险管理"；等老大先问出来，性质就变成"你没想到"。

各节展示动作

  • 框架能力：四个数字条读一遍；架构图手指右侧括号——"注意这个 79/21，是风险节的伏笔"（埋钩子）；Gherkin 示例读一遍那三行英文——"报告直接长这样，BA 不看代码能复述这条用例在验证什么"。八张能力卡只点一两张，其余"细节文档里有"。

三 · 分节讲稿（照读版）

每节一段，可直接读

02 框架能力 · 约 90 秒 "这一节证明一件事：这不是方案设想，是已经落地的框架。四个数字——14 条用例本地全部实跑通过、两千四百多行框架代码、28 个页面模型文件、两个分支并行维护。架构一句话：业务语言到页面细节是单向依赖；右边这个 79 比 21，是后面风险节的伏笔。往下这张能力对照总表是给您省时间的：上半区是对齐区——genie 支持的，BDD 用例组织、数据驱动、并行、重试、多环境切换、API 造数、数据库落地验证、报告、多浏览器——我们逐项都有；而且 genie 侧我是从宽标注的，没逐条核实的都按它有算，即便如此结论也不变。下半区是增量区——自动等待、worker 级并行、UI 调试模式、步骤编译期检查、AI 测试工装链——这些 genie 不具备，我们已经落地。这张表一句话总结：genie 有的都有，genie 没有的也有。"
03 三方案对比 · 约 90 秒 "三个候选放在一起，对比的主轴一句话：Playwright 官方的 Test runner 只存在于 Node 侧——Java 和 Python 拿到的是浏览器驱动，不是完整测试平台。先说 genie 真实的优势，这两格我特意标了绿色：Cucumber-JVM 官方维护、生态最成熟；genie 全家桶的报告和流水线开箱即用。这些是真优势，我不回避。但请看等待机制这一行：genie 的封装不支持自动等待，用例稳定性要靠显式等待一处一处堆——这是引擎级差距，桥不过去，下一节有实测数字。我的结论保持克制：Java 项目 genie 仍是合理默认；但 trade portal 是 TS 前端项目，匹配度在我们这边。"
04 实测数据 · 约 60 秒 "上一页是能力表，这一页是数字，四组对比用的是同一条业务用例。重点看两组：第一组，并行扩展——worker 数从 1 到 2 到 4，两边的耗时曲线【照图读数字】；第二组，显式等待密度——同一条用例 genie 侧写了【N】处显式等待，我们是零处，这就是自动等待在用例层的直接体现。第四组是失败诊断：同一个失败，我们这边拿到的是 trace——可以时间旅行回放的现场【条件允许当场打开】。"
05 风险专题 · 约 2 分钟（放慢） "这一节回答今天最尖锐的问题：playwright-bdd 是个人维护的开源项目，停更了怎么办。第一，先看事实：它是构建期的代码生成器，生成的是标准 Playwright 测试，运行时它不存在——锁定版本可以稳定使用以年计，不存在'跑着跑着坏了'。第二，看这个条形图：架构上把耦合面压到了 21%，绿色这 79% 的代码根本不知道它存在。第三，退出路径——这句话请允许我强调：迁移成本不是我估算的，是做过一遍量出来的。我们真的维护着一个不用 BDD 的镜像分支，同样的用例、原生写法、完整实现了一遍。真要退出，改的就是那五百行接线层，其余原样保留。"
06 下一步 · 约 30 秒 "下一步五件事，但今天请您确认的只有第一条：选型本身。其余四条——接共享测试环境、CI 分片并行、报告平台对接、核心回归铺开——都是选型确认之后的执行项，不需要今天拍板。"
四 · Q&A 预案

按被问概率排序

Q1 · 公司有 genie，为什么另起炉灶？必问

"不是对 genie 的否定，是匹配度问题。genie 给我们的是集成面——Cucumber、报告、流水线，这些我可以通过标准报告格式桥接回去，下一步计划里有这条。但两个引擎级差距桥不过去：一是它的封装不支持自动等待，用例稳定性要靠显式等待一处一处堆，那是 flaky 的最大来源；二是并行靠 fork JVM，进程启动和内存开销随并行度线性涨。我们被测系统本身是 TS 前端，同语言意味着前端同事能直接读懂甚至贡献页面模型。Java 项目我仍然建议默认 genie。"

答案里必须出现"genie 仍是 Java 项目的默认"——姿态是补位不是替代。有实测数据时直接翻到实测对比节。
Q2 · playwright-bdd 停更了怎么办？必问

"三层兜底。第一层，它是构建期的代码生成器，跑起来的就是纯 Playwright 测试，锁定版本可以稳定用以年计；第二层，架构上耦合面压到了 21%，八成的代码不知道它存在；第三层是实证——我们维护着一个不用它的镜像分支，同样的用例原生写法跑通了，真要退出，改的就是五百行接线层。"

Q2b · 除了退回原生，还有别的退路吗？能不能我们自己维护它？可能

"有，退路完整说是一个四级阶梯，一级比一级动作大。第一级，版本锁定——它是构建期工具，锁住版本可以稳定用以年计，期间什么都不用做。第二级，fork 自维护——它是 MIT 协议的 TypeScript 项目，法律上随意 fork；关键是我们要维护的面很窄：全仓对它的使用清单只有八项，真正脆弱的只有它对 Playwright 内部配置加载的兼容层，Playwright 大版本升级时可能要补一次，量级是天不是月。而且它是构建期工具，坏了编译立刻红，不存在运行时静默出错——自维护一个'坏了会大声喊'的工具，风险可控。第三级，退到 Cucumber.js——SmartBear 官方维护：Gherkin 文本逐字保留、步骤匹配串原样搬（两边用的是同一套 cucumber-expressions），丢的是 Playwright runner 的 fixtures 和调试集成；自动等待不丢，它是引擎能力不是 runner 能力。第四级，退回原生 Playwright——保住全部 runner 能力，Gherkin 降级为 step 标题，这条已经用镜像分支演练过。四级动的都是同一份五百行接线层，79% 的代码在任何一级都原样不动。选哪级，取决于当时为什么要退。"

fork 选项主动讲会加分——它把"个人维护"从威胁翻转成"最坏情况我们接得住"。两个必须点到的词：MIT（法律干净）、构建期失败是响的（自维护安全的根据）。Cucumber 一问参见此卡第三级，不必单独展开代价细节：代码面与原生退路同量级（~500 行），只是保留/丢弃的东西相反。
Q3 · genie 底层不也是 Playwright？你说的差距从哪来？大概率

"底层是同一个浏览器驱动，但封装层丢了 Playwright 最核心的两样东西：自动等待和 web-first 断言。用例层面感受到的稳定性差距全部来自这里——实测对比第 2 组直接数的就是这个：同一条用例，genie 侧要写 N 处显式等待，我们是零。"

这题是送分题，把话题引向实测对比节。
Q3b · AI agent 那套，给 genie 也配一套不就行了？大概率

"理论上可以，我拆开说。agent 体系分三层：规则和设计那一层是纯文本，Java 项目完全可以用；浏览器探索层面向的是应用不是框架，也能用。卡住的是执行层——'跑测试、停在错误现场、检查页面、改代码、重跑'这个自动回路。微软把这套 harness 作为官方产品只随 Node 版发布，我们是改配置就用上了；Java 侧要自建等价物。而且就算建成，有两样东西拖累它：agent 的工作方式是高频'改一点跑一次'，genie 每次迭代都要付编译加 fork JVM 启动的成本，这个延迟对 agent 是乘法惩罚；更关键的是 genie 没有自动等待，flaky 底噪高，自动修复回路分不清真回归和时序噪音。所以准确的说法不是 Java 做不到，而是：同样的投入，Node 侧的 agent 已经在干活，Java 侧还在造工具。"

这题是 Q3 的 agent 版本。主动承认"可以自建"，可信度反而上升——对照表里 genie 那格的备注就是这么写的，口径一致。
Q4 · 跑过真机吗？效果如何？可能

"14 条用例本地已经全部跑通，今天可以现场跑一条给您看。下一步是接入共享测试环境和 CI 分片并行。"

如果现场条件允许，直接跑——一条用例 + trace viewer，比任何回答有力。
Q5 · 谁来维护？团队都是 Java 背景怎么办？可能

"框架把维护成本压在纪律上：Locator 只允许出现在 POM 层且有收口规则、业务措辞有六条规范约束、数据全走 YAML——写用例的人接触的表面积很小。TS 对 Java 背景的 QA 语法迁移成本不高，真正要学的是 Playwright 本身，这个成本三个方案是一样的——而且 genie 那套显式等待的写法学起来并不比 auto-wait 简单。"

需要你自备：团队里谁接、占多少人力（见第五节清单）。
Q6 · BDD 值不值？写用例会不会更慢？可能

"我们对这个问题做的不是判断而是实验：两个分支并行维护，同样的用例 BDD 写法和原生写法各一份。结论是写的速度差别不大，差别在读——Gherkin 报告 BA 能直接读。而且 BDD 是可选薄层，今天选了以后随时能退。"

Q7 · 镜像分支不是双倍维护成本吗？可能

"不是实时同步，是低频按需同步——POM、数据、API 层本来就共用，每次同步的只有接线层。它的定位是保险单，保费很低。"

Q8 · 怎么接我们的报告平台 / 流水线？可能

"Playwright 原生输出 JUnit XML，Allure 也有现成 reporter，接内部平台是一次性工作，在下一步计划第三条。"

Q9 · 万一 Playwright 本身不行了呢？可能

"Playwright 是微软维护的行业事实标准。而且这层风险和选 genie 完全一样——genie 底层也是 Playwright，这不是方案之间的差异项。"

关键是最后一句：把"Playwright 风险"从你的方案剥离，它是所有候选共担的。
Q10 · 多久能覆盖核心回归？可能

"建模成本已经量化：trade portal 91 条元素收敛成 28 个文件；复用已有步骤时新增一条用例就是几行 Gherkin。核心回归清单有 N 条，按此估算约 X 周。"

N 和 X 需要你会前定好（见第五节清单）——这题不能现场即兴。
五 · 会前清单

需要你自备的弹药

  • 实测对比四组数据：按文档第 03 节的固定口径跑出图表替换占位（对比 1 速度、对比 2 显式等待密度、对比 3 代码量、对比 4 失败产物）。最少先出 2——一个数字就能讲。
  • 现场演示预热：本地跑通一条建仓用例 + 预先生成一份失败 trace，trace viewer 提前打开放在后台标签页。
  • 人力安排：谁维护、占多少时间（Q5 的下半句）。
  • 核心回归规模估算：N 条用例、约 X 周（Q10 不能即兴）。
  • genie 补课：确认它有没有 TS 支持路线图、报告平台的接入格式要求——对比表任何一格被当场纠错都会伤害整份文档的可信度。
  • AI 工装链被追问时的展示：终端预开仓库，30 秒动作：ls .claude/agents .claude/skills + cat 一个 agent 定义——"这不是概念，是仓库里的文件"。
